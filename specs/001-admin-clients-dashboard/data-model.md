# Data Model: Admin Clients Dashboard

**Feature**: `001-admin-clients-dashboard` | **Date**: 2026-11-07 | **Research**: [research.md](./research.md)

All schema changes ship in **one additive Prisma migration** (`admin_clients_dashboard`). Every
change either adds a nullable or defaulted column or creates a new table, so the release that
is running keeps working while the migration is applied (constitution VI).

## 1. Client (existing table `clients`, changed)

| Field | Type (Prisma → Postgres) | Rules | Change |
|---|---|---|---|
| `id` | `String @db.Uuid` | PK, generated by the service | - |
| `name` | `VarChar(255)` | required, trimmed, 1–255 characters, not unique | - |
| `businessCategory` | `VarChar(255)` → `business_category` | required, trimmed, 1–255 characters | - |
| `fbPageId` | `VarChar(255)?` → `fb_page_id` | optional, 5–30 digits, **unique** | - |
| `instaAccountId` | `VarChar(255)?` → `insta_account_id` | optional, 5–30 digits, **unique** | - |
| `accessToken` | `Text` → `access_token` | required on create, AES-256-GCM encrypted with the row id as AAD, hidden by the global `omit`, **never returned** | - |
| `brandLogo` | `VarChar(255)?` → `brand_logo` | optional, `http`/`https` link, **at most 255 characters** | Zod max reduced from 500 to 255 |
| `aiConfig` | `Json` → `ai_config` | see 1.1 | - |
| `dmReplyConfig` | `Json` → `dm_reply_config` | see 1.2 | input rule added |
| `commentReplyConfig` | `Json` → `comment_reply_config` | see 1.3 | - |
| `version` | `Int @default(1)` | starts at 1; +1 on every edit that changes something; unchanged by token replacement | **new** |
| `createdAt` / `updatedAt` | `DateTime` | managed by Prisma | - |

**Relationships (unchanged)**: Deleting a client cascades to `BusinessInfo`, `Service` and `Offer`
(`onDelete: Cascade`) and unlinks `User.clientId` (`onDelete: SetNull`). The delete dialog lists
these effects (FR-019).

### 1.1 `aiConfig` (AI reply settings)

| Key | Type | Rules | Default |
|---|---|---|---|
| `language` | enum | `ARABIC` \| `ENGLISH` \| `ENGLISH_ARABIC`, required | `ARABIC` |
| `brandVoice` | string | optional, trimmed, at most 400 characters | absent |

The schema allows extra keys (`catchall`). The dashboard edits only the two keys above and
sends any other existing keys back unchanged.

### 1.2 `dmReplyConfig` (private-message settings)

| Key | Type | Rules | Default |
|---|---|---|---|
| `enabled` | boolean | required | `false` |
| `likes_enabled` | boolean | required | `false` |
| `replies` | string[] | at most 50 items, each trimmed, 1–1000 characters | `[]` |

**Input-only rule (FR-026)**: `enabled = true` requires `replies.length ≥ 1`. The rule is
applied on the create and update schemas only, not in the database reader (see research R8).

### 1.3 `commentReplyConfig` (comment settings)

| Key | Type | Meaning | Default |
|---|---|---|---|
| `enabled` | boolean | public replies and hiding of complaint or insulting comments | `false` |
| `likes_enabled` | boolean | like comments | `false` |
| `inquiry_can_dm` | string[] | public reply to a question when the private message was sent | `[]` |
| `inquiry_can_not_dm` | string[] | public reply to a question when it couldn't be sent | `[]` |
| `engagement` | string[] | thank-you reply to positive comments | `[]` |

Each list holds at most 50 messages of 1–1000 characters. An empty list means the platform's
built-in default messages are used (FR-026).

### State: version lifecycle

```text
create ──► version = 1
edit with no differences ──► unchanged (no activity entry)
edit with differences, matching version ──► version + 1, entry UPDATED(changedFields)
edit with a stale version ──► refused (409 CLIENT_VERSION_CONFLICT), nothing written
token replacement ──► unchanged version, entry ACCESS_TOKEN_REPLACED
delete ──► row removed (cascade), entry DELETED (kept)
```

## 2. ClientActivity (new table `client_activities`)

The activity record required by FR-028. Entries can't be changed after they are written, and
there is no update or delete path.

| Field | Type (Prisma → Postgres) | Rules |
|---|---|---|
| `id` | `String @id @default(uuid()) @db.Uuid` | PK |
| `clientId` | `String @db.Uuid` → `client_id` | **no foreign key**, so it survives client deletion |
| `clientName` | `VarChar(255)` → `client_name` | client name at the time of the action |
| `actorId` | `String @db.Uuid` → `actor_id` | **no foreign key**, so it survives deletion of the admin account |
| `actorName` | `VarChar(255)` → `actor_name` | admin name at the time of the action |
| `actorEmail` | `VarChar(255)` → `actor_email` | admin email at the time of the action |
| `action` | enum `ClientActivityAction` | `CREATED` \| `UPDATED` \| `DELETED` \| `ACCESS_TOKEN_REPLACED` |
| `changedFields` | `String[] @default([])` → `changed_fields` | for `UPDATED` only: top-level field names, e.g. `["businessCategory","commentReplyConfig"]`; **never values** |
| `createdAt` | `DateTime @default(now())` → `created_at` | time of the action |

**Indexes**: `@@index([clientId, createdAt])`, used for "latest change to this client" in the
409 response; `@@index([actorId])`; `@@index([createdAt])`.

**Write rule**: Each entry is created in the same `prisma.$transaction` as the change it
records. If either write fails, both roll back (FR-021).

**Retention**: No job deletes entries, which meets the "at least 1 year" requirement. A
retention policy can be added later without a schema change.

## 3. Session (existing table `refresh_tokens`, extended)

The Prisma model keeps the name `RefreshToken` to avoid churn. It now represents a sign-in
session (research R2).

| Field | Type | Rules | Change |
|---|---|---|---|
| `id` | `String @db.Uuid` | session id, carried as the `sid` claim in access JWTs | - |
| `userId` | `String @db.Uuid` | FK to `users`, `onDelete: Cascade` | - |
| `tokenHash` | `String @unique` | SHA-256 of the 32-byte random cookie value; the raw value is never stored | - |
| `expiresAt` | `DateTime` | **absolute** limit: sign-in time + 12 h | meaning defined |
| `lastUsedAt` | `DateTime @default(now())` → `last_used_at` | idle limit: refresh refused when `now - lastUsedAt ≥ 30 min` | **new** |
| `revokedAt` | `DateTime?` → `revoked_at` | set on sign-out; a revoked session can't be refreshed and its access tokens are rejected | **new** |
| `createdAt` | `DateTime` | sign-in time | - |

**State transitions**:

```text
sign-in ──► active (lastUsedAt = now, expiresAt = now + 12h)
refresh within limits ──► active (lastUsedAt = now)
30 min without refresh ──► idle-expired (refresh refused, row kept)
now ≥ expiresAt ──► expired (refresh and access tokens refused)
sign-out ──► revoked (revokedAt = now)
password change ──► existing rule (tokens issued before passwordChangedAt are rejected)
```

Expired and revoked rows are harmless. A cleanup of rows past `expiresAt` can run in a later
feature; the `@@index([expiresAt])` index already exists.

## 4. Sign-in failure counter (Redis, not Postgres)

| Key | Value | Expiry |
|---|---|---|
| `auth:login-fail:<sha256(lowercased email)>` | failure count (integer) | 900 s from the first failure; reset to 900 s when the count reaches 5 |

- **Block rule**: count ≥ 5 → refuse sign-in without checking the password.
- **Reset**: a successful sign-in deletes the key.
- **Location**: the key prefix is a constant in `src/auth/consts/` (constitution VII).

## 5. Read models (API response shapes)

- **`ClientRecord`**: every `Client` field except `accessToken`, with the JSON columns parsed by
  the readers, and now including `version`. Returned by list, detail, create and update.
- **`PaginatedResult<ClientRecord>`**: `{ data, meta: { total, page, limit, totalPages } }`,
  unchanged.
- **`AuthSession`**: `{ user: SafeUser, token: string }`, returned by login and refresh. Login
  already returns this shape.

The full shapes are in [contracts/admin-api.openapi.yaml](./contracts/admin-api.openapi.yaml).
